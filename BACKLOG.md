# Later

- Internal cluster transport: use streamed NDJSON for every shard-forwarded bulk write, including operations that return hydrated objects. Keep request transport independent from response policy: minimal requests return counts, while hydrated requests may return full JSON objects. Queries, aggregations, and small cluster-control messages can remain JSON unless streaming provides a measurable benefit.

- Reference query planner: optimize predicates like `owner.object.name` by querying the referenced collection first, converting matching referenced IDs into base reference-value filters such as `owner.value: { "$in": [...] }`, and then using the normal field indexes on the owning collection. This should work generally for nested references where each hop can be resolved through indexed reference fields.

- Durable tombstone garbage collection: eventually remove database and collection tombstones once no retained snapshot or journal predates the deletion, every active peer has acknowledged it, and a stale peer cannot replay the deleted generation. Prefer generation/epoch IDs or an equivalent durable cluster watermark so cleanup remains safe across restarts and delete/recreate cycles.

- Local warm-tier storage for large object parts:
  - Treat tiering as an internal storage optimization only. Public reads must return normal hydrated objects with no `_warm`, `_cold`, or storage hints.
  - Keep hot data in memory and move configured warm payloads to local disk, not S3. S3 remains the durable snapshot/journal/restore layer.
  - Derive warm payload locations from `database/collection/objectId`; do not store per-field storage pointers in user objects.
  - Make the warm layer bulk-first: `putMany`, `getMany`, and `deleteMany`. Lists should narrow/page from hot memory/indexes first, then hydrate only the returned batch. Snapshots should hydrate in bounded batches and write full logical objects into the existing snapshot format.
  - Collection meta uses `tiering` directly. It can be a single policy such as `{ "keep": [...] }` or `{ "offload": [...] }`, or an ordered array of policies such as `{ "when": { "status": "archived" }, "keep": [...] }`. Do not use a nested `rules` key. `keep` and `offload` are mutually exclusive per policy, and `_id` is always kept.
  - Tiering policies may use simple query predicates in `when`; evaluate them on insert, replace, patch, restore, and future background retiering after meta changes. Do not add read/query-time tiering evaluation.
  - Indexed warm fields remain queryable because indexes are built from the full incoming object before splitting. Fields used for indexes, column indexes, permissions, references, routing, and common sorting must remain available to the relevant hot/index structures. Non-indexed warm-field queries should be a visible slow path or a later explicit policy decision.
  - Meta changes that require retiering large datasets should be background work later; the meta update itself should not synchronously rewrite millions of objects.

- Browser persistence through IndexedDB:
  - Treat IndexedDB as the browser equivalent of S3, using the existing persistence manager, logical key layout, full-object snapshot segments, manifests, `latest.json`, journals, tombstones, checkpoint ordering, retention, and snapshot-plus-journal restore flow. Do not create a separate browser persistence model.
  - Add a browser object-storage adapter for the existing `put`, `get`, `list`, and delete contract. Store the same JSON/JSONL payloads as records or blobs and restore them through the shared bulk-load path.
  - Do not add a second browser WAL by default. The durable IndexedDB journal transaction is the browser durability point; a WAL and journal in the same IndexedDB database would duplicate serialization, storage, and cleanup. Server filesystem WAL and S3 behavior remain unchanged.
  - Preserve bulk-first acknowledgement: memory acknowledgement may persist asynchronously, while durable acknowledgement waits for one atomic IndexedDB journal transaction per bounded bulk. Concurrent small writes may use bounded group commit. Never acknowledge a failed or quota-exceeded durable transaction.
  - Request persistent origin storage where available and expose whether it was granted. Report `navigator.storage.estimate()` usage/quota, snapshot and journal bytes, estimated next-checkpoint space, resident logical bytes, and the configured memory budget.
  - Enforce memory and persistent-storage headroom before accepting writes or starting a checkpoint. Snapshot retention remains configurable; account for the temporary old-plus-new snapshot footprint, publish the new manifest before pruning, and never delete the last valid snapshot first.
  - Restore and checkpoint in bounded batches with event-loop yields. Retained snapshots stay on disk; only the latest snapshot and following journals are restored. The live dataset plus indexes, columns, vectors, references, dictionaries, compression state, and working batches must still fit in browser memory.
  - Prevent concurrent independent browser runtimes from checkpointing the same persistent database. Use an exclusive origin lock for the database lifetime in the first implementation; do not add leader election or cross-tab replication initially.
  - Keep persistence platform seams isolated: browser code must not load Node, AWS, filesystem-WAL, or `Buffer` dependencies, and server behavior/performance must remain unchanged. Validate reload, interrupted checkpoints, journal recovery, quota failures, metadata/deletion recovery, multi-tab exclusion, and large restore/checkpoint behavior in real browsers.
